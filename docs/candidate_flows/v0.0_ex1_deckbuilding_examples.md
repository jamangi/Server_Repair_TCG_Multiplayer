# Candidate flow v0.0 ex1 — Deckbuilding

> **Status: explicitly non-authoritative example fixture.** This document tests one complete Decks experience. It does not approve collection rules, deck legality, deterministic shuffles, account persistence, balance, or UI behavior. Read it with the [Candidate-Frozen Example Profile v0.0](v0.0_ex1_decisions.md) and the [example board, 34-card catalog, exact decks, and draw fixtures](v0.0_ex1_board_and_cards.md).

Every `EX1-*` handle is local to this review package. It is not a stable card, deck, account, or shuffle ID.

## Replay vocabulary

The flow keeps definition, ownership, preparation, and runtime state separate:

| Object | What the player is inspecting | Authority boundary |
| --- | --- | --- |
| Card definition | One shared `EX1-CARD-*` rules fixture in the 34-card catalog. | Content fixture; not an owned copy or match instance. |
| Owned copy | Account collection permission to include that copy in a saved deck. | Private account state. Acquisition never edits a deck. |
| Draft entry | A local, unsaved card code and count. | Reversible local state until Save. |
| Saved deck | Exactly 30 entries by count, no more than three copies of one card code. | Authoritative account state after validation. |
| Selected deck | One saved deck chosen for Campaign, Co-op, or Competitive context. | Private account state; Ready snapshots it. |
| Deterministic variant | A review-only full permutation such as `EX1-SHUFFLE-G1-A`. | Replay fixture selected at match setup, not part of deck construction or normal random choice. |
| Opening hand | The first five instances named by a compatible deterministic variant. | Created only for that replay. |
| Card instance | One match-owned runtime copy in hand, deck, discard, or Bench. | Created after match setup; it is not edited in Decks. |
| Equipment / qualification | Separately owned preparation or permission. | Never consumes a deck slot or becomes a card implicitly. |

The two shared legal definitions are:

- [`EX1-DECK-BENCH-HARDWARE`](v0.0_ex1_board_and_cards.md#ex1-deck-bench-hardware), the memory, power, RAID, and thermal deck; and
- [`EX1-DECK-SYSTEMS-FIELD`](v0.0_ex1_board_and_cards.md#ex1-deck-systems-field), the network, RAID, thermal, boot, and storage deck.

Neither contains an Installed card. The account equipment in the equipping flow changes neither list.

## Flow DB-1 — Inspect the collection and create a legal saved deck

### Narrative context

Mara (`EX1-ACCOUNT-MARA`) sees a forthcoming hardware-focused shift on the Shift Desk. They want a separate saved copy of the known legal Bench Hardware deck so later experiments cannot overwrite the reviewed fixture. They plan to inspect the collection, duplicate the template, try a few edits, validate, restore the exact reviewed composition, save, and select it for Campaign.

### Screen-by-screen flow

1. **Inspect preparation on `Shift`.**
   - **Screen:** `SCR-SHIFT` shows the active lot summary, current Campaign deck, a `30 / 30` legality summary, and **Prepare**.
   - **Player intent:** select **Prepare deck**.
   - **Result:** local navigation to `SCR-DECKS`; no account or match state changes.
   - **Visibility:** active-lot context is player-safe; collection and deck details are `PRIVATE_PLAYER` account state.
   - **Motion:** `M-01` preserves the dock and identity while the central stage fades and shifts 8 px.
   - **Reduced motion:** replace the stage immediately, focus `Decks`, and announce the route.

2. **Read the Deck Library before editing.**
   - **Screen:** the Library lists the two shared definitions, selected-context badges, last saved revision, card count, maximum copy count, and validation status.
   - **Inspection:** Mara opens `EX1-DECK-BENCH-HARDWARE` and sees its complete list by reference to the board fixture: 30 cards, 21 definitions, maximum count 2.
   - **Boundary:** opening a deck does not select, Ready, shuffle, or instantiate it.
   - **Accessibility:** `Legal`, `30 / 30`, and `maximum 2 / allowed 3` are text, not color-only marks.

3. **Inspect the owned-card collection.**
   - **Screen:** the collection panel can filter by Owned, Test, Command, Repair, Verify, linked domain subject, Action cost, and eligibility.
   - **Card detail:** selecting a card shows its `EX1-CARD-*` definition, owned-copy availability, count in this draft, cost, target, disposition, linked domain records, and any qualification or equipment prerequisite.
   - **Boundary:** diagnostic cards already bundle the temporary Tool or Command access named in the board catalog. The builder does not require a second enabling equipment card.
   - **Failure recovery:** if ownership or content has not synchronized, Add remains unavailable with **Retry collection sync**. The UI does not assume the copy exists.

4. **Create from the reviewed template.**
   - **Modal:** `MOD-DECK-CREATE` offers Blank and the two exact example templates.
   - **Player intent:** choose **Copy Bench Hardware**, name the account copy `Mara — Bench Review`, and select Campaign as the intended context.
   - **Local result:** a draft containing the exact 30 entries from `EX1-DECK-BENCH-HARDWARE` opens. It is labeled **Unsaved copy**; no authoritative account object exists yet.

5. **Exercise reversible editing.**
   - **Player intent:** remove the one `EX1-CARD-MIN-CONFIG` entry, then inspect possible replacements. The draft becomes `29 / 30` and **Incomplete**.
   - **Result:** the owned card moves from draft to collection through local shared layout. No card copy is destroyed or acquired.
   - **Motion:** `M-04` moves the row between collection and draft after the local edit.
   - **Reduced motion:** update both lists and validator count instantly without moving focus.
   - **Reasoning:** Mara decides the reviewed fixture is preferable and chooses **Restore template**, returning the exact 30-card list. The restore is still local and reversible.

6. **Open the validator deliberately.**
   - **Drawer:** `DRW-DECK-VALIDATOR` checks exact size 30, copy limit at most 3, owned copies, card-definition availability, qualification/equipment requirements, selected context, and content revision.
   - **Result:** the restored template reads **Legal for Campaign**. The drawer says `Installed assets: none required` and does not treat the equipped caddy as a deck entry.
   - **Visibility:** validation details remain private account preparation; only the eventual Ready/Not Ready result is public in a Room.

7. **Save the new copy.**
   - **Authority request:** `SaveDeck(name, exactEntries, intendedContext, expectedAccountRevision)`.
   - **Pending state:** the local draft remains visible and labeled **Saving**. Animation does not declare success.
   - **Authoritative result:** the server validates ownership and the profile rules, creates a new saved-deck revision, and returns **Legal**.
   - **Motion:** the saved badge settles only after acceptance. Reduced motion updates the badge and focuses the success summary.
   - **Network recovery:** if the request fails before acceptance, the local draft remains intact with **Retry**, **Keep local draft**, and **Cancel**. No empty or partial authoritative deck is created.

8. **Select the deck for Campaign.**
   - **Player intent:** choose **Use for Campaign**.
   - **Authority request:** `SelectDeck(savedDeckRevision, Campaign, expectedAccountRevision)`.
   - **Result:** the account returns a new selected-deck revision. The original shared definition and Systems Field selection for other contexts remain unchanged.
   - **Boundary:** selection does not create a hand, choose a deterministic order, or Ready the player.

9. **Return to Shift and audit the exit state.**
   - **Screen:** `SCR-SHIFT` now shows `Mara — Bench Review · Legal · 30 / 30`.
   - **Exit state:** the saved copy exactly matches `EX1-DECK-BENCH-HARDWARE`; Campaign selection points to the copy; no match exists; no deterministic variant or opening hand exists; collection and equipment are unchanged.
   - **Motion:** `M-01`; reduced motion replaces the route and focuses the selected deck summary.

## Flow DB-2 — Recover from legality and account-version conflicts

### Narrative context

Mara wants to test an edit without damaging the legal Campaign selection. The flow exposes two different failures: a local rules violation and an authoritative account conflict. Neither failure may spend cards, alter a selected deck, or leak match state.

### Screen-by-screen flow

1. **Open a safe draft copy.**
   - **Screen:** from `SCR-DECKS`, Mara chooses **Duplicate for editing** on `Mara — Bench Review`.
   - **Result:** a local 30-card draft opens. The currently selected Campaign revision remains untouched.

2. **Create a visible copy-limit error.**
   - **Player intent:** set `EX1-CARD-VISUAL` from 2 copies to 4 without removing another entry.
   - **Local validator result:** `32 / 30` and `4 / 3 copies` appear as two separate errors. If the account owns fewer than four copies, ownership appears as a third independent error rather than being conflated with copy limit.
   - **Motion:** affected rows use `M-04`; the validator count updates after each draft edit.
   - **Reduced motion:** update text immediately and keep focus on the increment control.

3. **Attempt Save while invalid.**
   - **Authority boundary:** the client blocks the ordinary Save request because its displayed validator is invalid. If a stale client nevertheless submits, the account service returns `DECK_NOT_LEGAL` with safe, plain-language violations.
   - **State:** the invalid draft remains local; the saved Campaign selection remains the prior legal revision.
   - **Motion:** `M-14` gives one restrained nudge and focuses the validator summary.
   - **Reduced motion:** no nudge; focus the error summary. No card moves.

4. **Recover the reviewed list.**
   - **Player intent:** choose **Restore saved revision**.
   - **Result:** local entries return to the exact 30-card Bench Hardware composition; validator returns **Legal**.
   - **Boundary:** this discards only the local invalid edits, not owned copies or account history.

5. **Make a metadata edit and encounter a version conflict.**
   - **Player intent:** change the account-copy display name to `Mara — Hardware Continuity` and submit Save using the revision originally opened.
   - **Failure fixture:** another signed-in surface has advanced the saved-deck revision. The account returns `DECK_VERSION_CONFLICT`; it does not silently use last-write-wins.
   - **Modal:** `MOD-DECK-CONFLICT` shows **Current saved**, **Your local draft**, and the fact that their 30-card compositions are identical while names differ.
   - **Visibility:** the conflict contains only Mara's private account state.

6. **Recover by saving as a new copy.**
   - **Player choice:** choose **Save as new copy** rather than overwrite the newer revision.
   - **Authority request:** a new `SaveDeck` intent uses the latest account revision and the exact legal entries.
   - **Result:** success creates the separately named copy. Campaign selection still points to its prior saved revision until explicit selection.
   - **Motion:** accepted copy appears once in the Library. Reduced motion inserts it and announces the new name.

7. **Select explicitly.**
   - **Player intent:** choose **Use for Campaign** on the new copy.
   - **Result:** after authoritative revalidation, the selected badge moves to the new copy. A saved edit never selected itself.

8. **Exit-state audit.**
   - **Legal saved compositions:** every saved copy used here still matches the exact 30-card Bench Hardware list.
   - **Rejected states:** the 32-card/four-copy draft and stale-version Save never became authoritative.
   - **Unchanged:** collection inventory, Systems Field deck, equipment, qualification, match resources, and Worklog.

## Flow DB-3 — Select a deterministic replay variant without redefining the deck

### Narrative context

A reviewer wants to replay the documented games exactly. This is a review fixture, not a normal player choice over random outcomes. The reviewer must select a deck-compatible permutation and see the opening-hand identity before starting.

### Variant compatibility table

| Deterministic variant | Required exact deck definition | Opening-hand fixture |
| --- | --- | --- |
| `EX1-SHUFFLE-G1-A` | `EX1-DECK-BENCH-HARDWARE` | `EX1-HAND-G1-A` |
| `EX1-SHUFFLE-G1-B` | `EX1-DECK-SYSTEMS-FIELD` | `EX1-HAND-G1-B` |
| `EX1-SHUFFLE-G2-A` | `EX1-DECK-BENCH-HARDWARE` | `EX1-HAND-G2-A` |
| `EX1-SHUFFLE-G2-B` | `EX1-DECK-SYSTEMS-FIELD` | `EX1-HAND-G2-B` |

1. **Open `Review fixture` from the legal deck detail.**
   - **Screen:** an Advanced disclosure lists compatible replay variants and states: `Review-only deterministic order; not stored in the deck and not available as a normal matchmaking advantage.`
   - **State:** the saved deck remains a 30-card multiset with no order.

2. **Choose an incompatible variant on purpose.**
   - **Player intent:** with Bench Hardware selected, choose `EX1-SHUFFLE-G1-B`.
   - **Authority result:** `VARIANT_DECK_MISMATCH`. The response names the required public fixture deck but reveals no Ticket answer or future card beyond the already published replay catalog.
   - **State:** selected deck, account state, and Room readiness remain unchanged.
   - **Motion:** `M-14`; reduced motion focuses the compatibility error.

3. **Choose the compatible Game 1 variant.**
   - **Player intent:** select `EX1-SHUFFLE-G1-A`.
   - **Result:** the review setup validates the exact deck fingerprint and displays `EX1-HAND-G1-A` plus the published 25-card draw stack from the board fixture.
   - **Boundary:** the hand is a setup preview for the documented replay. Runtime card instances are not created until match initialization.

4. **Switch to the Game 2 replay.**
   - **Player intent:** choose `EX1-SHUFFLE-G2-A` while the same Bench Hardware multiset remains selected.
   - **Result:** setup now points to `EX1-HAND-G2-A`. No deck entry changes and the Game 1 permutation is not “discarded” because variants are fixture data, not cards.

5. **Exit without starting.**
   - **Exit state:** account still selects the legal saved deck; no hand, draw stack, score, Actions, Search Tokens, or Refresh Token has been instantiated.

## Flow DB-4 — Ready-lock rejection and recovery

### Narrative context

Mara is already **Ready** in a Room with Bench Hardware snapshotted. They notice a possible edit and open Decks from the persistent shell. The example tests whether account navigation can coexist with Room presence without mutating live preparation.

1. **Inspect while Ready.**
   - **Screen:** `SCR-DECKS` is readable, but mechanical edit controls state **Locked while Ready**. Room presence persists in the shell.
   - **Visibility:** other Room members see Mara's Ready state and selected deck legality summary, not the private list or collection.

2. **Submit from a stale surface.**
   - **Failure fixture:** an older tab submits a mechanical `SaveDeck` or `SelectDeck` intent.
   - **Authority result:** `LOADOUT_LOCKED_WHILE_READY`. No deck revision, Room snapshot, Ready state, hand, or match state changes.
   - **Motion:** `M-14`; reduced motion focuses the reason and offers recovery choices.

3. **Choose `Leave Ready and edit`.**
   - **First request:** `SetReady(false)` succeeds. The public lobby status changes to **Not Ready**.
   - **Second step:** Decks unlocks only after the new Room/account snapshot arrives.
   - **Motion:** `M-03` updates Ready status; reduced motion changes the text and announces it without a pulse.

4. **Edit, validate, and save.**
   - **Player behavior:** Mara opens a safe local draft, decides not to change the reviewed composition, and saves only after the validator reads 30 cards and maximum count at most 3.
   - **Result:** the account returns an accepted deck revision. Ready remains false.

5. **Select and re-Ready explicitly.**
   - **Requests:** `SelectDeck` revalidates the deck for the Room; then a separate `SetReady(true)` snapshots it.
   - **Failure recovery:** if the host changed relevant settings between those requests, Ready is rejected with the named incompatibility and the current safe Room revision. Mara may select another legal deck or leave.
   - **Result:** only a successful explicit Ready changes the public status.

6. **Exit-state audit.**
   - **Room:** Mara is Ready only after successful resnapshot.
   - **Deck:** exact accepted revision identified; still 30 cards and within copy limit.
   - **Variant:** none in normal Room play unless the Room is the explicit replay fixture.
   - **Match zones:** no hand, discard, Bench, Worklog action, or utility resource changed during deck editing.

## Failure and recovery matrix

| Failure | What remains unchanged | Recovery |
| --- | --- | --- |
| Collection/content not synchronized | Saved decks, selection, and Room state. | Retry synchronization before Add or Save. |
| Draft has 29, 31+, or too many copies | Authoritative saved deck and owned copies. | Follow validator links; edit locally; submit only when legal. |
| `DECK_NOT_LEGAL` from a stale client | Selected deck and Ready snapshot. | Install safe validation response, repair draft, resubmit a new intent. |
| `DECK_VERSION_CONFLICT` | Latest server deck and local draft. | Compare; reload, merge, or Save as new copy. No silent overwrite. |
| `VARIANT_DECK_MISMATCH` | Deck entries and account selection. | Choose the variant paired with the exact fixture deck. |
| `LOADOUT_LOCKED_WHILE_READY` | Deck, Ready snapshot, and match state. | Explicitly leave Ready, edit, validate, select, then Ready again. |
| Settings changed before Ready | Account deck remains saved. | Read the new Room requirements and choose a compatible deck or leave. |

## Motion and accessibility audit

- `M-01` handles shell navigation; reduced motion replaces the stage and moves heading focus.
- `M-03` presents accepted Ready changes; reduced motion updates and announces the status text.
- `M-04` presents local collection/draft movement; reduced motion updates both lists without moving focus.
- `M-13` presents real collection, account, content, and Room synchronization; reduced motion uses a text checklist with no decorative spinner.
- `M-14` presents rejected Save, variant, selection, or Ready intents; reduced motion focuses the error with no nudge.
- The account or match engine commits state before presentation. No animation callback validates a deck, consumes an owned copy, chooses a variant, clears Ready, or starts a match.
- Counts, errors, ownership, selection, context, Ready, and variant compatibility always have text. Color, movement, portraits, and sound are supplementary.

## Final exit state

At the end of the complete deckbuilding example:

- the reviewed Bench Hardware composition remains exactly the board fixture's 30 cards;
- the invalid 32-card/four-copy draft never became authoritative;
- a selected account copy is legal for Campaign;
- a Room edit, when exercised, required leaving Ready and explicitly becoming Ready again;
- deterministic variants remain review-only setup fixtures paired with the exact deck definitions;
- no opening hand or card instance exists until a match starts; and
- equipment, qualifications, owned cards, saved deck entries, and match Installed assets remain distinct.
