> **Status: non-authoritative example fixture.** This document does not freeze rules, approve balance, update schemas, or define implementation behavior. It temporarily resolves open questions only so the linked example flows can be replayed and criticized. Frozen authority remains in [`FROZEN_RULES.md`](../design/decisions/FROZEN_RULES.md).

This file is the package's [Candidate-Frozen Example Profile v0.0 decisions document](v0.0_ex1_decisions.md); the self-link gives every artifact one consistent profile target without implying higher authority.

## Purpose

This profile answers one design question: **what is the smallest coherent card game that can demonstrate the intended evidence loop without turning it into seven isolated departments or a one-way state machine?**

The answer used throughout this package is:

```text
Observe -> Diagnosis [Hypothesize <-> Test -> Isolate] -> Repair -> Verify -> Document
                        ^                                  |
                        `------ failed Verify -------------'
```

The words describe the function of an event, not a board lane that permanently owns a Ticket. A Ticket can contain observations, Evidence, machine changes, Verify results, and Worklog records from several iterations at once.

## Profile at a glance

| Area | Candidate-Frozen Example Profile v0.0 choice |
| --- | --- |
| Match shape | Exactly three starting Tickets, no refill, score termination disabled. |
| Deck | 30 cards, no more than three copies of one example card. |
| Opening | Five cards, three Search Tokens, one Refresh Token. |
| Turn | Draw one, receive two Actions, take paid actions in any order, then end. |
| Hypothesis | Free, revisable private marker containing up to two public candidates. |
| Tests | Distinct card executions that create immutable Evidence events. |
| Isolation | One-Action evidence-citing commitment checked against authored requirements. |
| Repair | One-Action eligible Repair card after accepted Isolation; changes machine state only. |
| Verify | One-Action authored Verification card. Failure creates Evidence and reopens Diagnosis. |
| Document | Document Live costs one Action and recovers its source card once. A valid closure bundle costs zero Actions in the immediate post-Verify window or on a later active turn. |
| Visibility | Detailed Evidence is private in competitive and team-visible in co-op until published. |
| Worklog | Immediate public placeholder in event order; later Documentation enriches it in place. |
| Score | Example-only pending causal records for one deepest accepted Isolation and its matching necessary Repair settle only at closure. Closure itself awards no Service Points. |
| Ending | Third closure ends the fixture. Co-op clears the queue; competitive high score wins. |

## Inherited frozen behavior

The profile relies on these approved foundations without reopening them:

- one configurable match system supports competitive and cooperative play;
- cooperative Service Points use a shared pool while individual contributions remain attributable;
- live play is server-authoritative, while an offline training match may use a local authoritative engine;
- Tickets are shared and jointly actionable unless an explicit effect creates ownership;
- Ticket progress belongs to the Ticket;
- faults and causal chains remain hidden until rules legitimately reveal them;
- Evidence uses `SERVER_ONLY`, `PRIVATE_PLAYER`, `TEAM`, and `PUBLIC_MATCH` visibility;
- cooperative Evidence is team-visible by default and competitive Evidence private by default;
- the server serializes actions, validates expected revisions, and rejects stale intents;
- computer technicians receive only player-safe information;
- Room membership, Player seats, and Spectator roles are explicit and separate;
- queue reconciliation follows the complete closure transaction; and
- closure is a zero-Action, non-scoring event with Player/team statistical attribution;
- a successful final Verify opens an immediate closure-resolution window before automatic end-turn;
- the exact causal-contribution policy remains unfrozen;
- the game has no account/loadout Equipment system and Qualifications are recognition-only honor badges; and
- authoritative timers, clocks, disconnect grace, and reconnect synchronization do not live in animation code.

See [Frozen Rules §§2–16](../design/decisions/FROZEN_RULES.md).

## Temporary rules decisions

### EX1-RULE-001 — Deterministic three-Ticket fixture

Every replayable example uses:

```text
starting_ticket_count (S) = 3
queue_minimum (Q) = 0
termination_score (X) = -1
turn timer (T) = disabled
player clock (PT) = disabled
disconnect grace (W) = 60 seconds in live examples
```

The three Tickets are selected fixtures rather than random draws. The third closure completes the game after its entire closure transaction. Cooperative players win by clearing the queue. Competitive players compare Service Points; equal totals are co-winners for this example instead of invoking an undocumented tiebreaker.

**Why:** finite three-Ticket games are short enough to audit and satisfy the frozen configurable-match ranges. They expose queue-empty and score-attribution questions without pretending those questions are settled.

**Sources and pressure:** [Frozen Rules §2](../design/decisions/FROZEN_RULES.md#2-one-configurable-match-system), unresolved [`SCORE-001`](../design/decisions/UNFROZEN_RULES.md#score-001), and the recommended finite-cleanup presets in [`RECOMMENDED_PRESETS.json`](../design/RECOMMENDED_PRESETS.json). The exact Ticket selection and no-timer parameters are fixture choices; finite `Q = 0` queue-clear and winner/tie behavior are inherited rather than reopened.

### EX1-RULE-002 — Deck, hand, draw, and Actions

- Legal deck size is exactly 30.
- A deck may contain at most three copies of one example-local card code.
- Each Player draws a named five-card opening hand.
- Each turn, including the first, begins by drawing one card if the draw deck is nonempty.
- Each Player receives two Actions after the draw.
- Card cost is printed as 0, 1, or 2 Actions. Zero-Action cards remain limited to one copy of that card name per turn unless their text says otherwise.
- A Player may end the turn with unused Actions.
- There is no hand limit in this profile.
- One-shot cards go to discard after resolution. Installed or persistent technical Tool cards remain in their defined match zone until an effect removes them. Repair and Verify cards are one-shot records even when their fictional part or result persists in machine state.

**Why:** this inherits the frozen first-version envelope while retaining example-local costs for the named 0-, 1-, and 2-Action cards.

**Sources:** [Frozen Rules §9](../design/decisions/FROZEN_RULES.md#9-first-version-deck-round-and-turn-rules) and [Card Types](../design/02_CARD_TYPES.md). Individual card costs remain fixture balance outside the frozen turn envelope.

### EX1-RULE-003 — Search, Refresh, and non-loss exhaustion

- Each Player starts with three Search Tokens; storage cap is five.
- Spend one Search Token and one Action to choose one card from the remaining draw deck, put it in hand, then shuffle the draw deck.
- Each Player starts with one Refresh Token and may hold at most one.
- Spend one Refresh Token and one Action to combine discard and remaining draw deck, shuffle them, and create a new draw deck. Installed cards and cards in hand do not move.
- After a Ticket closes, every active Player gains one Search Token up to five and returns to one Refresh Token.
- An empty draw deck skips the draw. It does not cause loss, concession, or exhaustion in this profile. Cardless core actions remain available. None of the fixtures intentionally reaches this boundary.

**Why:** the utility economy keeps specialized decks dependable without creating a second universal currency in hand. Skipping an empty draw avoids importing the obsolete mandatory-draw-loss wording from the older overview.

**Sources:** [Frozen Rules §10](../design/decisions/FROZEN_RULES.md#10-search-and-deck-refresh) and the completed overview entry in [`DOCUMENTS_TO_UPDATE.md`](../design/DOCUMENTS_TO_UPDATE.md#top-level-design-review).

### EX1-RULE-004 — Round and turn order

A round contains one turn for each currently active Player in fixed seat order. A solo round contains one turn. A turn is:

1. install the latest authoritative snapshot and settle required reconnect state;
2. draw one card;
3. receive two Actions;
4. revise a Hypothesis freely before, between, or after paid actions;
5. take paid actions whose total cost does not exceed the two Actions;
6. if a successful Verify completes the current requirements, resolve the immediate zero-Action closure window before checking automatic end-turn; and
7. otherwise end voluntarily or automatically when no Actions remain.

Server resolution pauses clocks if a timed room later adopts them. Narrative dialogue and decorative animation occur outside the actionable clock.

**Sources:** [Frozen Rules §6](../design/decisions/FROZEN_RULES.md#6-timers-and-disconnection), [Frozen Rules §9](../design/decisions/FROZEN_RULES.md#9-first-version-deck-round-and-turn-rules), and the [UI accessibility boundary](../story/gameplay_candidates/APP_SHELL.md#accessibility-and-reduced-motion).

### EX1-RULE-005 — Authored candidate universe and Hypotheses

Each Ticket exposes a public authored candidate set of three to five stable Fault IDs. The server separately holds the true Fault instance or causal chain.

A Player may use the free **Revise Hypothesis** basic action on their turn to mark up to two unresolved public candidates. It costs no Action, creates no score, and has no truth-revealing server response. In competitive play the marker is `PRIVATE_PLAYER`; in cooperative play it is `TEAM`. It can be documented voluntarily, but no generic free-text conclusion becomes authoritative.

**Why:** a finite authored set makes card outcomes and Isolation auditable. Keeping Hypotheses lightweight preserves ordinary human reasoning while still giving the interface a comparison aid.

**Sources:** [Frozen Rules §11](../design/decisions/FROZEN_RULES.md#11-candidate-faults-hypotheses-and-tests), the [case-study Hypothesis candidate](../case_studies/v0.1/candidate_materials/cardless-actions.md#create-or-revise-a-candidate-fault-set), and the [story cardless-action boundary](../story/gameplay_candidates/CARDLESS_ACTIONS.md#create-or-revise-a-hypothesis-set).

### EX1-RULE-006 — Tests and Evidence

Playing a Test or Command card creates one immutable action event and one attached result, even if an earlier execution used the same card name. An authored result may:

- `SUPPORT` a candidate;
- `CONTRADICT` a candidate;
- `RULE_OUT` a candidate;
- `CONFIRM` a candidate or fault instance;
- reveal another observation; or
- be `INCONCLUSIVE`.

The Ticket fixture controls the result; card text never reads hidden state directly. A repeated Test is legal when its target or machine state changed. The server rejects an identical same-target, same-state repeat as `NO_NEW_ELIGIBLE_OUTCOME`; the card and Action are not spent and no Worklog event is created.

Test Evidence changes Knowledge State, not machine state. A deliberately named substitution Test uses a temporary known-good resource that is removed after comparison; the permanent Repair still requires a Repair card. This artificial separation keeps the base profile's Repair gateway clear and is identified as a gameplay abstraction.

**Sources:** [Frozen Rules §11](../design/decisions/FROZEN_RULES.md#11-candidate-faults-hypotheses-and-tests), [case observations 002 and 004](../case_studies/v0.1/candidate_materials/decision-observations.md#case-obs-002--isolation-needs-evidence-standards-not-one-universal-test-shape), and [Data Architecture §Test](../design/01_DATA_ARCHITECTURE.md#test).

### EX1-RULE-007 — Evidence-gated Isolation

**Commit Isolation** is a universal one-Action basic action. The Player selects one public candidate and cites the Evidence events that satisfy the Ticket's authored Isolation requirement.

- If the candidate is a true actionable Fault and every cited requirement is met, Isolation succeeds.
- The isolated Fault, contributor, cited Evidence references, actionable/deepest label, and acceptance time become Ticket-owned `PUBLIC_MATCH` progress.
- If the commitment is false or insufficient, the Action is spent, the server returns only `ISOLATION_NOT_SUPPORTED`, no machine state changes, and the Player loses eligibility for this fixture's pending deepest-Isolation contribution on that Ticket. The response does not distinguish wrong candidate from insufficient Evidence.
- Other Players may continue testing before or after accepted Isolation, but an ordinary Repair becomes legal once the matching public Isolation exists.

**Why:** manual commitment preserves accountability; public accepted Isolation keeps jointly actionable Ticket progress usable by every seat. The generic failure response discourages candidate guessing from becoming a free oracle.

**Sources:** [Frozen Rules §12](../design/decisions/FROZEN_RULES.md#12-evidence-supported-isolation-and-repair-gateway) and the [case-study Isolation candidate](../case_studies/v0.1/candidate_materials/cardless-actions.md#commit-an-evidence-supported-isolation).

### EX1-RULE-008 — Repair gateway and machine state

An ordinary Repair:

- costs its printed Action amount, normally one;
- requires a public accepted Isolation of a Fault targeted by the referenced Repair Procedure;
- consumes/discards the Repair card after resolution;
- appends a machine-state change and repair-history event; and
- never marks Verify, Documentation, or closure complete.

Unsupported and speculative Repairs are rejected before payment. The profile contains no parts-cannon exception. Diagnostic substitutions are Tests and revert after comparison as described above.

**Why:** the frozen core requires Test and Repair to remain separate events. A real intervention that both changes state and reveals information may inspire two explicitly linked records, but it is not a dual Test/Repair event or an implied follow-up core candidate in this profile. Any later combined-event exception would require an explicit rule-change task.

**Sources:** [Frozen Rules §11](../design/decisions/FROZEN_RULES.md#11-candidate-faults-hypotheses-and-tests), [Frozen Rules §12](../design/decisions/FROZEN_RULES.md#12-evidence-supported-isolation-and-repair-gateway), and [case observations 004 and 008](../case_studies/v0.1/candidate_materials/decision-observations.md#case-obs-004--a-repair-action-may-simultaneously-be-a-diagnostic-substitution).

### EX1-RULE-009 — Verify requirements and reopening Diagnosis

Each Ticket names one or more required Verification cards and explicit success conditions. A Verify execution costs the card's printed Actions and creates a distinct result.

- A pass satisfies only its named condition.
- All required conditions must have current passes after the latest relevant Repair.
- A failure or inconclusive result becomes Evidence, preserves prior events and machine changes, invalidates any now-stale pass, and changes the Ticket to **Returned to Diagnosis**.
- The Ticket fixture may append an authored observation or Fault-instance context legitimately implied by the failed condition, without changing the public candidate set or exposing server-only truth.
- Players resume Hypothesize and Test. A new accepted Isolation can gate another Repair.
- A later pass does not erase the earlier failure.
- A failed Verify settles no pending contribution. A final successful Verify opens the immediate zero-Action closure-resolution window before the normal no-Actions end-turn check.

**Why:** disappearance of a symptom, service restoration, and fault-specific acceptance are not assumed equivalent. The `EX1-T04 Ready for Rebuild` fixture requires array health, so a stalled rebuild necessarily reopens Diagnosis.

**Sources:** [Frozen Rules §13](../design/decisions/FROZEN_RULES.md#13-verify-and-return-to-diagnosis), [case observations 001 and 007](../case_studies/v0.1/candidate_materials/decision-observations.md#case-obs-001--negative-verification-can-reopen-diagnosis), and [Card Types §7](../design/02_CARD_TYPES.md#7-verification-cards).

### EX1-RULE-010 — Incremental Documentation and closure bundle

**Document Live** is a universal one-Action basic action available while a Ticket is active, including during Diagnosis and after failed Verify. It targets one undocumented authoritative card action and its attached eligible result.

After all current Verify conditions pass, the active Player may instead publish the mandatory **closure bundle** containing the accepted Isolation, its cited Evidence, every Repair in the accepted path, all failed Verify results in that path, and the current passing Verify results. The closure bundle costs zero Actions and does not recover a card.

Successful final Verify opens an immediate closure-resolution window before the normal automatic end-turn check, including when Verify spent the second Action. If that window closes without publication, the eligible Ticket remains jointly actionable and a later active Player may publish its zero-Action bundle. Closure has no owner, first refusal, or point reward.

Documentation creates a public projection of those records. It does not move or rewrite the original event. The Worklog retains event sequence and action time, then adds publication time and publisher. Already team-visible Evidence in co-op remains team-visible and gains a public projection. A published record is immutable; it cannot be documented twice for another reward.

Document Live returns the published action's source card from discard to its owner's hand once. The recovered card retains no private result; playing it again creates a new action and Evidence event. This inherited frozen recovery creates a strategic publication tradeoff in the replay; the fixture demonstrates that consequence without reopening its cost, once-only recovery, or the draw/Search/Refresh envelope.

The closure bundle is mandatory. Free-form notes may be displayed as non-authoritative flavor, but closure is derived only from structured records.

**Why:** incremental publishing matches real case records and creates a competitive information decision, while one final bundle prevents paperwork from consuming several turns after the technical work is complete.

**Sources:** [Frozen Rules §14](../design/decisions/FROZEN_RULES.md#14-incremental-documentation-and-closure-record), [case observations 005–007](../case_studies/v0.1/candidate_materials/decision-observations.md#case-obs-005--documentation-evidence-supports-action-targeted-publication), and the [case-study Document candidate](../case_studies/v0.1/candidate_materials/cardless-actions.md#document-an-undocumented-action-and-its-attached-result).

### EX1-RULE-011 — Visibility and Worklog projection

At accepted non-closure card/basic-action event creation—including a card whose printed cost is zero—every participant receives a public Worklog placeholder containing:

- authoritative sequence;
- actor;
- Ticket;
- exact played card or named basic action;
- target Ticket or public surface, without a concealed component/fault target;
- Action cost; and
- action time.

Until Documentation:

| Record | Competitive actor | Cooperative team | Opponent / public / spectator |
| --- | --- | --- | --- |
| Card/basic-action identity, Ticket target, and Action cost | Public | Public | Public |
| Concealed component/fault target | Private | Team | Hidden until Documentation |
| Test result and Evidence | Private | Team | Hidden |
| Hypothesis marker | Private | Team | Hidden |
| Accepted Isolation | Public | Public | Public |
| Machine-state change from Repair | Public summary; exact action may remain hidden | Team detail plus public summary | Public summary |
| Verify pass/fail summary | Public because it changes Ticket eligibility | Public | Public |
| Undocumented supporting detail | Private | Team | Hidden |
| Documented projection | Public | Public | Public |

Documentation enriches the original placeholder in sequence position. A publication event at the current end links back to it. Spectators receive only `PUBLIC_MATCH`. SIFT, computer technicians, reconnect snapshots, animation, and accessibility announcements use the same projection rules.

A zero-Action closure creates its own public closure event and statistical attribution after validation. It never masquerades as a paid-action placeholder or reveals a private result outside the valid bundle.

**Sources:** [Frozen Rules §8](../design/decisions/FROZEN_RULES.md#8-evidence-and-worklog) and [Frozen Rules §14](../design/decisions/FROZEN_RULES.md#14-incremental-documentation-and-closure-record).

### EX1-RULE-012 — Example-local pending causal-contribution rubric

> **Non-authoritative scoring fixture; not <code>SCORE-001</code>.** The repository's exact contribution classes, values, duplicate policy, visibility, Root Cause policy, and cooperative aggregation remain unfrozen. These two one-point categories exist only so the deterministic examples still have auditable results.

Each Ticket can create exactly two pending records in this profile:

1. **Deepest Isolation contribution — pending 1 Service Point.** The first eligible Player whose accepted Isolation identifies the Ticket's authored deepest actionable Fault creates this record. A rejected Isolation on that Ticket removes that Player's eligibility for this category.
2. **Matching necessary Repair contribution — pending 1 Service Point.** The Player who performs the necessary Repair directly against that deepest accepted Isolation creates this record when the Repair remains in the final valid causal path.

Pending records are attributable but do not change score when created. Failed or inconclusive Verify settles nothing and preserves still-relevant pending records. Superseded, redundant, earlier non-deepest, or otherwise ineligible actions remain contribution statistics but do not score under this fixture.

Publishing a valid closure bundle settles the two still-relevant records atomically. In competitive play they go to their recorded Players. In cooperative play they enter the shared team pool while preserving individual origin. The closer receives a Player/team **closure statistic only** and no Service Point. For audit readability these example pending/settled rows are public; this does not decide the visibility question in <code>SCORE-001</code>.

**Why:** the rubric preserves the examples' causal emphasis and prior six-point match totals without paying for a convenience endpoint. Its deliberately narrow categories expose rather than solve the real scoring decision.

**Sources:** frozen non-scoring closure in [Frozen Rules §§14–15](../design/decisions/FROZEN_RULES.md#14-incremental-documentation-and-closure-record) and unresolved [`SCORE-001`](../design/decisions/UNFROZEN_RULES.md#score-001).

### EX1-RULE-013 — Complete closure transaction

Publishing a valid zero-Action closure bundle resolves atomically in this order:

1. validate that the current Isolation, Repairs, and Verify passes form a complete authored causal path;
2. enrich and lock the Worklog records;
3. settle the eligible pending records from EX1-RULE-012; closure itself awards no Service Point;
4. record Player/team closure statistics;
5. archive and remove the Ticket from the active queue;
6. grant one Search Token to each active Player up to five;
7. restore each active Player's Refresh Token to one;
8. reconcile the queue—creating nothing because <code>Q = 0</code>;
9. evaluate the three-Ticket terminal condition against the complete transaction; and
10. end the closer's turn.

No draw reward is attached to closure. It ends the turn even when an Action remains. When a successful Verify spent the second Action, the immediate closure window resolves before automatic end-turn.

**Sources:** [Frozen Rules §§14–15](../design/decisions/FROZEN_RULES.md#14-incremental-documentation-and-closure-record).

### EX1-RULE-014 — Targeting, revisions, rejection, reconnect, and departure

- A card or basic action names one active Ticket unless its text targets the Player's Bench, deck, or Worklog.
- Tickets remain jointly actionable; no example card claims ownership.
- Every intent includes an intent ID, expected match revision, actor, action, card/basic-action data, and target.
- A stale expected revision is rejected before payment with the current safe revision and a plain-language reason. No card moves and no Worklog event is added.
- Reconnect installs the latest player-safe snapshot first, then settles only explicitly supplied unseen semantic events. Duplicate event IDs are ignored.
- A Player disconnected beyond `W` concedes in a live example. A voluntary Concede confirms and converts the Player to Spectator when capacity permits; otherwise the Player remains joined with no gameplay role. In either case the Player receives no future turns. Leave removes Room membership and concedes if necessary.
- A cooperative match may continue with one human. A live match ends when no human remains.

**Sources:** [Frozen Rules §§3–7](../design/decisions/FROZEN_RULES.md#3-collaboration) and the [recommended player-safe projection](../design/RECOMMENDED_DATA_MODEL.md#player-safe-projections).

### EX1-RULE-015 — Computer technicians and Spectators

Computer technicians receive exactly the private/team/public view of their seat and choose only among legal actions exposed there. They cannot inspect hidden Ticket answers or server random state. Spectators receive public Worklog, public Ticket state, public scores, public turn status, and no hands, Hypotheses, or unpublished Evidence. Competitive spectator streams are live in these fixtures solely to keep the walkthrough compact.

**Sources:** [Frozen Rules §§4 and 8](../design/decisions/FROZEN_RULES.md#4-live-and-offline-execution) and the spectator-delay question in [Unfrozen §9](../design/decisions/UNFROZEN_RULES.md#9-multiplayer-teams-targeting-and-information-exceptions).

## Presentation and Motion contract for the examples

The engine commits state before presentation. Motion for React consumes semantic events; no rule, cost, visibility decision, or timer completion occurs in an animation callback.

| --- | --- | --- |

| `M-03` | Portrait moves to a new Room seat/role and readiness ring pulses once. | Update seat and status text, then announce it. |
| `M-04` | Deck card moves between collection and draft through shared layout. | Update both lists and validator count without moving focus. |

| `M-13` | Sync and reconnect progress reflect actual checks and safe snapshots. | Text checklist/progress only; no decorative spinner. |
| `M-14` | Rejected intent gives one restrained nudge and inline reason. | No nudge; focus the error summary. State remains unchanged. |
| `M-15` | Result sections reveal Observed -> Isolated -> Repaired -> Verified -> Documented -> Uncertainty after authoritative completion. | Show all sections immediately and focus the result heading. |

Color, movement, sound, and portraits are never the only state carrier. Narrative reading and decorative transitions never consume authoritative time.

## Alternatives deliberately not selected

| Alternative | Why not used in v0.0 examples |
| --- | --- |
| Global or dynamically unbounded Fault candidates | Difficult to audit and too encyclopedic for a first card-game fixture. |
| Hypothesis as a scored or card-gated action | Makes ordinary reasoning depend on economy before that benefit is proven. |
| Automatic Isolation when a Test confirms a Fault | Removes the accountable conclusion and conflates Evidence with commitment. |
| Private accepted Isolation in competitive play | Conflicts with simple jointly actionable Repair progress and creates awkward per-seat gateways. |
| Speculative Repair | Realistic in some cases, but obscures the teaching gateway and parts-cannon consequence in the first profile. |
| Successful Repair proves the diagnosis | Directly contradicts the project and case-study boundary. |
| End-only Documentation | Misses real mid-Diagnosis evidence records and removes the publication tradeoff. |
| Every documented element draws a card | Cannot be balanced independently of the total replenishment economy. |
| Separate rules engines for solo, co-op, and competitive | Contradicts the frozen configurable-match direction. |
| Department-locked lifecycle verbs | Conflicts with real role overlap, solo play, and the story foundation. |
| Omniscient SIFT or computer technician | Violates player-safe information and turns explanation into an oracle. |
| A closer Service Point or paid closure Action | Conflicts with frozen zero-Action, non-scoring closure and recreates closure sniping. |
| Account/loadout Equipment or mechanical Qualifications | Explicitly removed by Frozen Rules §16. |

## Risks the examples are meant to expose

1. Does public accepted Isolation make cross-Player Repair too easy or appropriately collaborative?
2. Does the example-only two-category causal rubric omit too much useful Test, Verify, or assist work?
3. Is a zero-Action final closure bundle too efficient compared with incremental Documentation?
4. Does a rejected Isolation still reveal too much, even with a generic response and lost bonus?
5. Are 0- and 2-Action technical cards worth their added teaching burden?
6. Does the separate-event presentation teach the Test/Repair boundary clearly enough? Any future combined or linked-event exception would require an explicit rule-change task rather than a change to this example profile.
7. Are authored public candidate sets educational scaffolding or an excessive reduction of real diagnosis?
8. Can a three-Ticket finite game expose enough deck cycling to evaluate Search and Refresh?
9. Should successful Verify be public immediately, or only its eligibility-changing summary?
10. Which honor-badge and cosmetic presentation belongs in public profiles without implying gameplay power?

## Review boundary

The [board, cards, decks, and Ticket fixtures](v0.0_ex1_board_and_cards.md) instantiate this profile. The focused and full flows must not silently add another rule. After review, useful choices should return individually to the normal decision lifecycle; the profile as a whole should never be promoted by copying it into frozen rules.
